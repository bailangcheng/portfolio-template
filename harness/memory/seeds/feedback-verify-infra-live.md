**基础设施・部署・发布相关的事实，必须先用 API/CLI 取得实状态再开口。**
不要把文档（Notion / docs / TODO 的 checkbox / 过去的日志）当作现状读。

**Why:** 短期内同一结构的错误犯了三次：
1. "CMS 是真内容" → 错。打开页面看的 = **读缓存**。当时生产在发假的。
2. "生产 Worker 未创建" → 错。**两天前就建好了**。信了没勾的 checkbox。
3. "域名还没绑，切 NS 后要绑" → 错。**两天前就绑好了**。差点照此跟外部厂商安排步骤。

**共同结构 = 错误的本体：**
- **代码的真相在仓库里（读一读就知道）。基础设施的真相只在"运行的系统"里。**
  基础设施不经 commit 就会变，所以文档必然滞后。**文档是意图，不是现状。**
- **接受了代理信号当证据。** 200 ≠ 正确的东西在跑；页面能看到内容 ≠ 取数活着；
  secret"已设置" ≠ 有效。

**How to apply:**
- 说任何基础设施状态之前，**先跑一条实查命令**。Notion 上写着也要查。
- **验证走直接证据。** 选"如果坏了会给出不同结果"的路径
  （例：打未预生成的路径。看 200 没有意义）。
- **实查到的事实当场写回记录。** 只说在聊天里不算记录 —— "不留记录"的实体就是这个。
- 自己的测试失败时，**先怀疑自己的测试路径，再怀疑被测系统**。
